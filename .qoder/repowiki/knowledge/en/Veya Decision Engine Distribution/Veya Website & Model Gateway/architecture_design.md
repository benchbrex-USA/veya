Two cooperating Python entry points under `web/`:
- `server.py` implements a `ThreadingHTTPServer` + `BaseHTTPRequestHandler` (`WebsiteHTTPServer`) that serves static assets from `web/static/`, renders HTML pages by templating `index.html` with titles/descriptions from `static/site-config.json`, and exposes `/api/infer`, `/api/health`, `/api/version`, `/api/benchmark`, `/robots.txt`, and `/sitemap.xml`. All inbound JSON is parsed via `contracts.parse_json`, whitelisted through `contracts.validate`, forwarded as `POST /v1/{primitive}` to the upstream model at `VEYA_MODEL_URL` (default `http://127.0.0.1:8080`), then revalidated through `contracts.validate_response` before being returned to the browser.
- `model_server.py` is a thin bootstrap that loads `artifacts/release/manifest.json` via `veya.release_bundle.load_release_manifest` and calls `veya.server.serve` on loopback port 8080 — it is the audited model process the website talks to.

Security boundaries are enforced in-process: per-IP sliding-window rate limiting (`_charge` with `CAPACITY=12`, window 60s) plus a `BoundedSemaphore(MAX_INFLIGHT=2)` gate; strict CSP/X-Frame-Options/Permissions-Policy headers; origin allow-listing against `VEYA_ALLOWED_ORIGINS`; `VEYA_PUBLIC_ORIGIN` must be HTTPS-only without path/query/fragment when binding to non-loopback hosts; request body capped at 32 KB and response at 524 KB; all upstream responses are size- and shape-checked via `UpstreamContractError`.

Dependency direction is one-way: `server.py` → `contracts.py` → upstream model; `model_server.py` depends only on `veya.release_bundle` and `veya.server`. The `static/` directory holds the client-side SPA (vanilla JS modules like `content.mjs`, `ui.mjs`, `playground.mjs`, `model-client.mjs` plus CSS/images) served verbatim.
